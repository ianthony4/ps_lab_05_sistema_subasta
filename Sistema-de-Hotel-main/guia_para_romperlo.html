Vulnerabilidades Críticas

Rompen la lógica de negocio central del sistema
🔴 CRÍTICO VULN-01 · Completar reservación SIN factura pagada → habitación se libera gratis reservationService.js · PATCH /api/reservaciones/:id/completar

El endpoint PATCH /api/reservaciones/:id/completar cambia la reservación a "completada" y libera la habitación sin verificar si existe una factura pagada. Es decir, un huésped puede hacer check-out sin pagar nunca. El test del equipo rival solo verifica que el estado cambie y la habitación se libere, pero nunca verifica que haya pago previo.

Crear huésped y reservación normalmente.
NO crear ninguna factura ni pago.
Llamar directamente a PATCH /api/reservaciones/{id}/completar.
El sistema devuelve 200 y marca la reservación como completada y libera la habitación.
La estadía fue sin costo. No se generó ninguna factura ni pago.
// 1. Crear reservación POST /api/reservaciones { "huespedId": "<id>", "habitacionId": "<id>", "fechaCheckIn": "2027-01-10", "fechaCheckOut": "2027-01-15", "numHuespedes": 1 } // 2. Completar SIN pagar — debería fallar pero NO lo hace PATCH /api/reservaciones/{reservacionId}/completar // → 200 OK 😱 ← estado: "completada", habitación libre, CERO pagos
🐛 Bug: Sistema acepta checkout sin pago Debería ser: 422 si no hay factura pagada
🔴 CRÍTICO VULN-02 · Doble reservación en la misma habitación con fechas solapadas reservationService.js · createReservation()

El código sí tiene validación de solapamiento, pero no hay ningún test en la suite del equipo rival que verifique este escenario. Si existe un bug en la lógica de solapamiento (condición de fecha exacta), se puede crear una segunda reservación que empiece el día que termina la primera (mismo día de checkout ↔ checkin), lo que generaría un conflicto real en el hotel.

Crear Reservación A: check-in: 2027-02-01 · check-out: 2027-02-05
Crear Reservación B (misma habitación): check-in: 2027-02-05 · check-out: 2027-02-08
La condición de solapamiento es: data.fechaCheckIn < r.fechaCheckOut && data.fechaCheckOut > r.fechaCheckIn
Con fechas exactas: 2027-02-05 < 2027-02-05 → false. El sistema ACEPTA la reservación.
La habitación queda "ocupada" pero con 2 reservaciones al mismo tiempo en sus límites de fecha.
// Reservación A ya existe { "fechaCheckIn": "2027-02-01", "fechaCheckOut": "2027-02-05" } // Reservación B — check-in = check-out de A → NO hay solapamiento según código POST /api/reservaciones { "habitacionId": "<misma habitación>", "fechaCheckIn": "2027-02-05", "fechaCheckOut": "2027-02-08", "numHuespedes": 1 } // → ¿409 o 201? — La habitación figura como OCUPADA, pero el solapamiento pasa
🐛 No hay test de solapamiento de fechas Debería ser: 409 Conflict siempre que la habitación ya tenga reservación activa
🔴 CRÍTICO VULN-03 · Facturar una reservación ya completada (post check-out) billingService.js · createBilling()

El servicio de facturación verifica que la reservación no esté cancelada, pero permite crear facturas sobre reservaciones ya "completadas". Esto significa que se puede generar una segunda factura después del check-out. El equipo rival no tiene ningún test que verifique este caso. Un huésped podría recibir dos cobros por la misma estadía si el sistema anula la primera y se genera una segunda.

Crear reservación → completarla (PATCH /completar).
Crear factura para esa reservación completada.
El sistema NO debería aceptarlo si la reservación ya fue completada sin pago previo.
Sin embargo el código solo rechaza si estado === 'cancelada'. Estado "completada" pasa sin problema.
// reservacion.estado = "completada" ya existe POST /api/facturacion { "reservacionId": "<id de reservación completada>", "metodoPago": "efectivo" } // → 201 Created 😱 ← Factura creada sobre reservación ya cerrada // Línea en billingService.js: // if (reservation.estado === 'cancelada') { ← solo bloquea canceladas // Falta verificar: if (reservation.estado === 'completada') → error
🐛 Bug: Factura permitida sobre reservación completada sin pago Debería ser: 422 si la reservación ya está completada

Vulnerabilidades de Severidad Alta

Generan estados inconsistentes o datos corruptos
🟠 ALTO VULN-04 · Actualizar habitación ocupada al estado "disponible" directamente roomValidator.js · PATCH /api/habitaciones/:id

El endpoint de actualización de habitaciones permite cambiar el campo estado a cualquier valor válido (disponible, ocupada, mantenimiento). Si una habitación está ocupada (tiene reservación activa), se puede forzar su estado a "disponible", permitiendo que otra persona la reserve mientras la primera reservación sigue activa. El equipo rival no testea actualizaciones de habitaciones.

Crear reservación para habitación X → el sistema la marca como "ocupada".
Usar el endpoint PATCH para cambiar el estado de esa habitación a "disponible".
Crear una segunda reservación para la misma habitación.
Ahora hay 2 reservaciones confirmadas para la misma habitación en el mismo período.
// Habitación X está "ocupada" por reservación activa PATCH /api/habitaciones/{habitacionId} { "estado": "disponible" } // Fuerza estado sin validar reservaciones activas // Ahora crear otra reservación en la misma habitación POST /api/reservaciones { "habitacionId": "<misma habitación X>", ... } // → 201 Created 😱 ← Dos reservaciones activas en la misma habitación
🐛 Bug: Estado de habitación desincronizado con reservaciones activas Debería verificar: no permitir cambiar a "disponible" si hay reservación activa
🟠 ALTO VULN-05 · Cancelar reservación con factura pendiente → factura queda huérfana reservationService.js · cancelReservation()

Si se cancela una reservación que ya tiene una factura en estado "pendiente", la factura queda en el sistema en un estado imposible: es "pendiente" de una reservación "cancelada". No existe test que verifique que al cancelar la reservación, la factura se anule automáticamente.

Crear reservación y luego crear su factura (estado: pendiente).
Cancelar la reservación (PATCH /reservaciones/:id/cancelar).
Consultar la factura: sigue en estado "pendiente" referenciando una reservación "cancelada".
Ahora intentar pagar esa factura → el sistema la acepta (no verifica si la reservación fue cancelada).
// 1. Crear factura → pendiente POST /api/facturacion { "reservacionId": "<id>", "metodoPago": "efectivo" } // 2. Cancelar reservación PATCH /api/reservaciones/{id}/cancelar // → 200 OK, reservación=cancelada, PERO factura sigue "pendiente" // 3. Pagar la factura huérfana PATCH /api/facturacion/{facturaId}/pagar // → 200 OK 😱 ← Pago de una factura de reservación cancelada
🐛 Bug: Facturas huérfanas al cancelar reservación Debería: anular automáticamente facturas pendientes al cancelar reservación
🟠 ALTO VULN-06 · Actualizar DNI de huésped a uno ya existente sin verificar unicidad guestValidator.js · validateGuestUpdate() · PATCH /api/huespedes/:id

Al crear un huésped, el sistema verifica que el DNI no esté duplicado. Sin embargo, en validateGuestUpdate() solo se valida el formato del DNI pero no su unicidad. Esto permite actualizar el DNI de un huésped al DNI de otro huésped ya registrado, creando inconsistencia en los datos. No existe ningún test de actualización de huéspedes en la suite del equipo.

Huésped A tiene DNI 12345678.
Huésped B tiene DNI 87654321.
Actualizar Huésped B con el DNI de A: PATCH /api/huespedes/{idB} → dni: "12345678"
El sistema acepta el cambio. Ahora dos huéspedes tienen el mismo DNI.
PATCH /api/huespedes/{idHuespedB} { "dni": "12345678" } // DNI que ya tiene el huésped A // → 200 OK 😱 ← Dos huéspedes con el mismo DNI en el sistema // En guestValidator.js validateGuestUpdate(): // Solo valida: /^\d{8}$/ — NO verifica duplicados // Falta: buscar en el store si otro guest ya tiene ese DNI
🐛 Bug: DNI duplicado permitido en actualización Debería: 409 si el DNI ya está registrado en otro huésped
🟠 ALTO VULN-07 · Descuento decimal no bloqueado (descuento=50.9 pasa como válido) billingValidator.js · validateBilling()

El validador de descuentos solo verifica el rango 0 ≤ descuento ≤ 50, pero no restringe que el descuento sea entero. Un descuento de 50.9 pasaría la validación (50.9 ≤ 50 es false → rechaza). Pero un descuento como 49.99 sería aceptado cuando el test del equipo solo prueba enteros. Adicionalmente, valores como 0.001 o 49.999 generan cálculos de IGV con errores de floating-point que no están documentados.

POST /api/facturacion { "reservacionId": "<id>", "metodoPago": "efectivo", "descuento": 49.999 } // → 201 Created — descuento acepta decimales infinitos // El cálculo: subtotal * 49.999 / 100 puede generar imprecisión de punto flotante // También probar: { "descuento": 0.001 } // ¿Genera igv correcto? { "descuento": 33.333 } // Un tercio exacto — posible error de redondeo
🐛 No probado: descuentos decimales y errores de redondeo Caso borde: descuento=49.999 → cálculo de IGV con floating-point

Casos No Cubiertos — Severidad Media

Brechas en cobertura que el equipo rival no testeó
🟡 MEDIO VULN-08 · Nombre con solo espacios en blanco pasa la validación guestValidator.js · sanitizeString()

La función sanitizeString() hace .trim() antes de validar la longitud. Si se envía un nombre como " " (solo espacios), el trim lo convierte en "" y se rechaza correctamente. Pero un nombre como "A " tiene longitud 1 post-trim y se rechaza. Sin embargo, "Ab " (2 chars útiles + espacio) pasa porque la longitud sanitizada es 2 = MIN. El test del equipo rival prueba "Ab" (2 chars) pero no prueba nombres con espacios intermedios excesivos.

// Casos no probados por el equipo rival: { "nombre": "A B" } // 3 chars con espacio — ¿pasa patrón NAME_PATTERN? { "nombre": " Juan " } // Espacios al inicio/fin — sanitiza pero ¿patrón? { "nombre": "Juan Carlos" } // Doble espacio — colapsa a "Juan Carlos" por replace(/\s+/g,' ') { "nombre": "Ñoño" } // Caracteres Unicode especiales — ¿pasa NAME_PATTERN? { "nombre": "María José" } // Tilde y acento — ¿qué dice NAME_PATTERN?
🐛 Sin cobertura: nombres con caracteres Unicode, tildes, Ñ Caso interesante: ¿"Ñoño" pasa como nombre válido de huésped peruano?
🟡 MEDIO VULN-09 · Check-in con fecha de HOY — comportamiento ambiguo reservationValidator.js · getTodayString()

La validación de check-in rechaza fechas pasadas con data.fechaCheckIn < today. Esto significa que check-in con fecha de hoy es aceptado. El equipo rival no probó este caso límite. En un hotel real, los check-in del día de hoy tienen reglas especiales (hora de check-in). Más importante: los tests del equipo rival usan getFutureDate(1) (siempre mañana), nunca prueban getFutureDate(0) (hoy).

// Caso no probado: check-in HOY POST /api/reservaciones { "fechaCheckIn": "<fecha de hoy YYYY-MM-DD>", "fechaCheckOut": "<mañana>", "numHuespedes": 1 } // Código: if (data.fechaCheckIn < today) → "hoy" NO es menor que "hoy" // → 201 Created — check-in HOY aceptado. ¿Es correcto?
🔍 No cubierto: reservación con check-in = hoy El test que falta: AVL-FECHA para fecha de hoy (límite)
🟡 MEDIO VULN-10 · Precio con más de 2 decimales en actualización no se valida roomValidator.js · validateRoomUpdate()

Al crear una habitación, el validador verifica que el precio no tenga más de 2 decimales. Pero en validateRoomUpdate(), esa verificación no está presente. Se puede actualizar el precio de una habitación a 100.123 y el sistema lo acepta. Esto puede generar errores de redondeo en todos los cálculos posteriores de facturas.

// Crear habitación normal POST /api/habitaciones { "numero": 500, "tipo": "doble", "precio": 200.00, "piso": 5 } // Actualizar con precio de 3 decimales — PASA sin error PATCH /api/habitaciones/{id} { "precio": 199.999 } // → 200 OK 😱 ← precio con 3 decimales → genera errores en facturación // En roomValidator.js validateRoomUpdate(): // Solo valida: precio en rango — SIN verificar decimales // Línea 117-124: falta el bloque de validación de decimales
🐛 Bug por omisión: actualización de precio sin validar decimales Cobertura faltante: tests de PATCH habitaciones con precios irregulares
🟡 MEDIO VULN-11 · Eliminar huésped con reservación activa no está restringido guestService.js · DELETE /api/huespedes/:id

El módulo de huéspedes tiene un endpoint DELETE /api/huespedes/:id. No existe ningún test que verifique si se puede eliminar un huésped que tiene una reservación activa. Si se permite esta operación, la reservación quedaría referenciando un huésped inexistente, corrompiendo la integridad referencial del sistema.

Crear huésped y crear una reservación confirmada para ese huésped.
Intentar DELETE /api/huespedes/{id}.
Si el sistema acepta: la reservación ahora referencia huespedId de un huésped inexistente.
Consultar la reservación: nombreHuesped aún existe en el objeto, pero el huésped no.
// Huésped tiene reservación confirmada DELETE /api/huespedes/{huespedConReservacion} // → ¿200 OK? o ¿422 Error? — El equipo rival NO probó este caso // Si devuelve 200: reservación queda huérfana // La reservación aún tiene huespedId que ya no existe en el store
🐛 Sin test: DELETE huésped con reservación activa Debería ser: 422 si el huésped tiene reservaciones activas
🟡 MEDIO VULN-12 · numHuespedes mayor a capacidad del tipo de habitación → ningún test lo cubre correctamente reservationService.js · ROOM_RULES.MAX_GUESTS_BY_TYPE

El sistema tiene capacidades por tipo: individual=1, doble=2, suite=4. El test PE-I-HUE3 rechaza 5 huéspedes con un 400, pero usa la habitación del seed sin saber su tipo real. Si la habitación del seed es una "suite" (capacidad 4), el test pasa por las razones equivocadas (el validador de formato rechaza 5 antes de verificar la capacidad del tipo). No hay test que intente reservar una habitación individual con 2 huéspedes.

// Ningún test prueba esto específicamente: // Habitación tipo "individual" (capacidad máx: 1) POST /api/reservaciones { "habitacionId": "<id de habitación INDIVIDUAL>", "numHuespedes": 2 // Supera capacidad de individual } // Debería ser 422 (excede capacidad) pero el equipo no lo testea // Tampoco se prueba: { "habitacionId": "<DOBLE>", "numHuespedes": 3 } // Supera cap. doble (2) { "habitacionId": "<SUITE>", "numHuespedes": 4 } // Exactamente al límite (válido)
🐛 Sin test: validación de capacidad por tipo de habitación Casos faltantes: 2 en individual, 3 en doble, 4 en suite (límite), 5 en suite
